# VRY fork notes — STATIX live-data backbone

This fork keeps the existing **VALORANT rank yoinker (VRY)** interface, configuration, web loadout view, chat, Discord RPC, stats, and upstream project identity. The engineering changes are intentionally concentrated in the live-data path and release plumbing.

## What changed

- The websocket remains the fast wake-up signal, but local Riot presence is also polled as a fallback so a dropped/coalesced event does not leave VRY stuck in the previous phase.
- Duplicate self-presence rows are filtered and ranked; VALORANT rows with a recognized `MENUS` / `PREGAME` / `INGAME` loop are preferred over incomplete or League-shaped duplicates.
- Confirmed `PREGAME` / `INGAME` state is sticky during uncertainty. Network failures, 429s, and malformed replies are not treated as proof that a match ended. Active → `MENUS` needs repeated local/GLZ evidence.
- Match discovery uses bounded retries to cover the short window where presence changes before GLZ player/match endpoints are ready. Stale match-detail objects are never used without current player membership.
- PREGAME player rank/stat work is cached and reused through the PREGAME → INGAME handoff, so allies do not need to be fetched again when opponents become visible.
- Riot HTTP calls use finite connect/read timeouts. Auth refresh is synchronized and bounded, worker sessions are reused, and 429/5xx/network failures create a short shared per-host cooldown to avoid retry storms.
- Static valorant-api metadata is cached and warmed in the background. Missing loadout/cosmetic metadata degrades to an empty cosmetic payload rather than blocking the core table.
- Rank and recent-match caches are thread-safe; same-match details are single-flight.
- Party/presence metadata is optional and defensive so a transient missing row does not crash the scoreboard.
- The built-in updater and status checks point only to `latenitekode/VALORANT-rank-yoinker`; this fork will not silently replace itself with upstream `mdevio` releases.
- Bundled documentation download/release counters also point to this fork; upstream author/license links remain as attribution.

## Windows release path

Normal users should use the frozen Windows artifact generated by `.github/workflows/build.yml`:

1. GitHub Actions installs Python **3.14.5** and project dependencies.
2. Regression tests run before packaging.
3. `cx_Freeze` builds `vry.exe` plus `python314.dll` and `lib/`.
4. `docs/`, `configurator.bat`, and `updatescript.bat` are included and verified.
5. The complete build directory is uploaded as a GitHub Actions artifact.

`START.bat` and `INSTALL.bat` are explicitly source/developer paths. `INSTALL.bat` now accepts the maintained Python 3.14.x line instead of rejecting it.

## Scope / authorship

The original ISC license and upstream authorship remain intact. This is a reliability-focused fork, not a redesign or rebrand.

## Validation limitation

Automated tests cover transition/membership logic, duplicate presence selection, bounded retry behavior, and cache behavior. A real Riot/VALORANT client session cannot be exercised in CI or this engineering environment, so final live-client verification should still cover MENUS → PREGAME → INGAME → MENUS, custom games, reconnects, and a rate-limited/degraded network case.
